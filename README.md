## 2. 数据集构建：为什么是"短时间窗口 + 用户级抽样 + 完整轨迹"

单机算力有限，直接截取 3~7 天仍有几千万行。三种方案的实际效果：

| 方案 | 做法 | 结果 |
|---|---|---|
| 时间窗口截取 | 取连续 N 天 | 7 天 = 7255 万行，单机跑不动 |
| 行级均匀随机抽样 | 每行独立按概率保留 | 行数能压下来，但**漏斗被破坏**：同一用户的浏览和购买被独立抽掉，总体 PV→购买 从 61.00% 掉到 0.90% |
| **本方案** | 用全区间活跃用户作抽样框 → 按用户随机抽 → 保留其**全部**行为 | 用户整取整舍，漏斗链路完整；行数可按目标规模收敛 |

**核心**：抽样单位是"用户"而不是"行"。被抽中的用户，他在整个数据区间（9 天）的所有行为一条不丢。

```bash
python src/taobao_dataset_build.py                          # 默认：前 1 天抽样框，抽 5% 用户
python src/taobao_dataset_build.py --window-days 2           # 前 2 天做抽样框
python src/taobao_dataset_build.py --scope window            # 只保留窗口内记录（不跨天取完整轨迹）
python src/taobao_dataset_build.py --no-auto-tune            # 强制 5%，不按行数上下限收敛
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--window-days` | 10 | 抽样窗口长度（天），覆盖数据全区间，消除抽样框偏差 |
| `--user-ratio` | 0.05 | 用户抽样比例（对用户均匀、无放回） |
| `--target-rows` / `--min-rows` | 500 万 / 100 万 | 行数上下限，超出时自动调整抽样人数 |
| `--scope` | full | `full` 保留完整轨迹；`window` 只保留窗口内 |
| `--seed` | 42 | 随机种子，保证可复现 |

脚本分三遍扫描原始文件（每遍只读需要的列）：

| 阶段 | 读取列 | 作用 | 耗时 |
|---|---|---|---|
| Pass A | timestamp | 逐时分布 → 数据主区间 → 抽样窗口 | 20 s |
| Pass B | user_id + timestamp + behavior_type | 每用户行数、窗口活跃用户、全量真实漏斗基准 | 28 s |
| Pass C | 全部 5 列 | 按抽中的用户过滤 + 清洗 + 排序 + 导出 | 40 s |

> 必须全量扫描：本文件是**按 user_id 排序**的，不是按时间排序，"只读前 1 天"无法靠提前结束读取实现。

### 实测结果

| 指标 | 值 |
|---|---|
| 原始数据 | 100,150,807 行 / 987,994 用户 |
| 脏时间戳剔除 | 44,269 行（最早 1902 年、最晚 2037 年） |
| 数据主区间 | 2017-11-24 23:00 ~ 2017-12-04 00:00 |
| 抽样窗口 | 2017-11-24 23:00 ~ 12-04 23:00（10 天，覆盖全区间，窗口内 100,107,354 行） |
| 抽样框（窗口活跃用户） | 987,991 人（即全体活跃用户，抽样框偏差归零） |
| 请求 5% | 49,400 人 → 预计 4,993,579 行，在 500 万上限内 |
| **最终抽样** | **49,400 人（5.000%）→ 4,993,579 行** |
| 输出数据集 | 274.6 MB，时间跨度 2017-11-24 23:00 ~ 12-03 23:59（完整 9 天轨迹） |

### 抽样偏差检验

| 口径 | PV→中间 | 中间→购买 | 总体 PV→购买 |
|---|---|---|---|
| 全量基准（987,991 用户） | 86.93% | 70.17% | **61.00%** |
| 抽样框基准（987,991 人，与抽样可比） | 86.93% | 70.17% | **61.00%** |
| 本数据集（49,400 人） | 86.97% | 70.32% | **61.15%** |

- **抽样误差（本数据集 vs 抽样框基准）：0.15 个百分点** → 用户级抽样本身几乎无偏
- **抽样框偏差（抽样框 vs 全量）：+0.00 个百分点** → 抽样窗口覆盖全区间后，"首日活跃用户偏活跃"的固有偏差被彻底消除

## 3. 会话切分与限时漏斗：口径决定结论

### 为什么必须切会话

第 2 节的漏斗是 **9 天累计"发生过"口径**——只要用户 9 天内浏览过、也收藏/加购过、也购买过就算转化，不管中间隔了多久。用户 11-25 随便逛了逛、12-03 才下单，也被算成"转化"，没有业务意义。

业界标准做法是**先切会话**：把用户连续行为按"超过 N 分钟不活跃"切成一段段会话，在**单个会话内部**看漏斗——同一个会话里的行为才算一次连贯的购物旅程。

```bash
python src/taobao_session_funnel.py                # 默认 30 分钟
python src/taobao_session_funnel.py --gap-minutes 15
python src/taobao_session_funnel.py --no-export    # 只算指标，不改 CSV
```

### 会话统计（30 分钟间隔）

| 指标 | 值 |
|---|---|
| 会话总数 | 826,508 |
| 人均会话数 | 16.73 |
| 每会话事件数 | 均值 6.04，中位数 3，P90 15，最大 518 |
| 会话时长 | 均值 700 秒，中位数 206 秒 |
| 单事件会话 | 256,181（31.0%） |

### 五种口径的转化率对比（同一份数据）

| 统计口径 | PV→购买 总体转化率 |
|---|---|
| 九天累计 · 出现过就算 | 61.15% |
| 九天累计 · 按先后顺序 | 37.46% |
| 单次会话 · 出现过就算 | 2.84% |
| **单次会话 · 按先后顺序（会话转化率）** | **1.32%** |
| **用户维度 · 会话内按序** | **17.26%** |

> 口径命名规则：前半段是**统计范围**（九天累计 / 单次会话 / 用户维度），
> 后半段是**判定方式**（出现过就算 / 按先后顺序）。不使用编号开头，也不使用行话。
>
> **同一份数据，转化率能从 1.32% 到 61.15%，差 46 倍。** 写结论时必须说明口径。
> 有业务意义的是后两行：
> - 单次会话 · 按先后顺序 1.32% = 会话转化率（含浏览的会话里，按序走完 浏览→收藏/加购→购买 的占比）
> - 用户维度 · 会话内按序 17.26% = 浏览用户中，"能在同一个会话内走完购买旅程"的比例

会话级漏斗明细：含浏览的会话 778,634 → 顺序到达收藏/加购 148,148（19.03%）→ 顺序走完购买 10,255（6.92% / 总体 1.32%）。
用户级漏斗明细：有浏览会话的用户 49,215 → 会话内浏览后收藏/加购 39,410（80.08%）→ 会话内走完三级 8,495（21.56% / 总体 17.26%）。

### 敏感度：不活跃间隔的选取影响

| 间隔(分钟) | 会话数 | 含浏览会话 | 会话顺序转化 | 用户级转化 |
|---|---|---|---|---|
| 10 | 1,030,665 | 960,378 | 0.74% | 12.46% |
| 15 | 937,531 | 877,892 | 0.97% | 14.54% |
| **30** | **826,508** | **778,634** | **1.32%** | **17.26%** |
| 60 | 731,963 | 693,032 | 1.69% | 19.38% |
| 120 | 628,182 | 597,716 | 2.23% | 21.59% |

间隔越长，会话被合并得越多，跨阶段的先后关系越容易凑出来，转化率因此上升。**30 分钟是 Google Analytics 等工具的行业默认值**，本项目取此值，并在报告里标注敏感度。

| 项 | 值 |
|---|---|

| 连接 | `localhost:3306`，`root` |
| 表 | `user_behavior`（4,993,579 行）、`session_summary`（826,508 会话）、`dataset_meta`（血缘 34 项）；洞察表见第 5 节 |

## 5. 业务洞察：用户画像、商品分级与关联推荐

```bash
python src/taobao_insights.py     # 全部计算在 MySQL 内完成（集合运算+窗口函数）-> 建洞察视图（约 2 分钟）
```

这一步把"明细 + 汇总"再往上叠一层**标签层**，把业务概念固化成可查询的表。计算逻辑全部写在 `sql/05_insights_compute.sql` 里，不再把明细拉进 pandas，数据规模放大也不会触发内存问题。

### 产出表

| 表 | 行数 | 说明 |
|---|---|---|
| `session_classic` | 778,634 | 会话级经典四层漏斗：浏览 → 收藏 → 加购 → 购买（会话内严格时序） |
| `user_classic` | 49,215 | 用户级经典四层漏斗（九天内严格时序） |
| `user_profile` | 49,400 | 用户画像与标签：决策风格、高价值、高购买潜力、偏好类目 |
| `item_profile` | 19,259 | 参评商品（浏览 ≥ 30）行为汇总与分级：高购买率 / 低购买率 / 普通，含流失定位 |
| `item_assoc` | 860 | 商品共购关联（"买了又买"），供关联推荐 |

### 标签口径

| 标签 | 判定规则 |
|---|---|
| 冲动型 / 理性型 | 复合评分：会话时长中位数、每会话行为数、行为规模三项相对分位按 0.5/0.3/0.2 加权成百分制，≥ 50 分为理性型，否则冲动型 |
| 高价值用户 | 有购买，且「0.5×购买频次 + 0.3×行为量 + 0.2×新近度」加权分进入购买用户前 20% |
| 高购买潜力 | 前提 = 存在加购或收藏但未下单的会话（意向闭环）；再按意向频次、会话深度、停留时长、类目聚焦度四项百分制加权，≥ 70 分入选 |
| 商品分级 | 浏览量 ≥ 30 的商品参与；按「购买 ÷ 浏览」转化率的上下五分位划档 |
| 低购买率流失定位 | 意向率低于参评商品中位数 → 问题在「浏览到意向」；否则 → 问题在「意向到购买」 |

### 实测结果

| 指标 | 值 |
|---|---|
| 会话级经典四层 | 浏览 778,634 → 收藏 56,194 → 加购 7,232 → 购买 651（总体 0.08%） |
| 用户级经典四层 | 浏览 49,215 → 收藏 19,152 → 加购 11,615 → 购买 6,573（总体 13.36%） |
| 冲动型 / 理性型 | 24,226 人（购买率 65.21%） / 25,174 人（购买率 71.15%） |
| 高价值 / 高购买潜力 | 6,752 人 / 9,728 人 |
| 商品分级 | 参评 19,259 件：高购买率 4,016、低购买率 4,502 |
| 低购买率流失定位 | 浏览到意向 2,852 件、意向到购买 1,650 件 |

> **四层漏斗在会话级几乎走不通**（总体 0.08%）：要求「浏览→收藏→加购→购买」四步在同一次会话内严格依次发生，而真实用户很少在一次会话里既收藏又加购再下单。用户级（九天累计）口径的 13.36% 更有参考价值。这也再次印证：**漏斗层级怎么切，直接决定转化率高低**。

### 洞察视图（13 个）

`v_classic_funnel_session`、`v_classic_funnel_user`、`v_consumer_type`、`v_hourly_behavior`、`v_peak_consumer`、`v_peak_value`、`v_high_potential_users`、`v_high_value_users`、`v_item_grade_summary`、`v_item_low_list`、`v_item_high_category`、`v_item_assoc_top`

## 6. 深度分析预计算：路径挖掘、留存分群与类目下钻

```bash
python src/taobao_deep_analysis.py     # 全量在 MySQL 内计算，产出五张小表（约 3.5 分钟）
```

看板里凡是需要**全量扫描明细**的分析（会话路径、首购留存、类目下钻），都在这一步
离线算好落成小表；页面只读小表，秒级响应。计算逻辑大量使用 MySQL 8 的
窗口函数与 `GROUP_CONCAT`，数据规模放大也无需改架构。

### 产出表

| 表 | 行数 | 说明 |
|---|---|---|
| `path_patterns` | 79 | 会话路径模式：82.65 万会话去重压缩后的路径分布、占比与转化率 |
| `path_transitions` | 12 | 会话内相邻行为的跳转量（供桑基图） |
| `user_cohort` | 45 | 首购分群留存：9 个首购日分群 × 首购后第 0~4 天的复购率 |
| `category_funnel` | 10 | 浏览量 Top10 类目的四类行为量与浏览→购买转化 |
| `hour_category` | 236 | 24 小时 × Top10 类目的购买量分布（时段运营排期用） |

### 关键口径

| 口径 | 规则 |
|---|---|
| 行为序列压缩 | `GROUP_CONCAT(behavior_type ORDER BY dt)` 提取会话内序列，连续相同行为合并为一步（pv pv fav → pv fav） |
| 长尾归并 | 会话数 < 200 的路径不单列，归并为「其他路径组合」，保证占比合计 100% |
| 首购分群 | 按用户**首次购买日**分组，`DATEDIFF` 计算距首购天数，复购率 = 当日购买用户 ÷ 分群规模 |
| 类目下钻 | 浏览量 Top10 类目（子查询外包派生表绕过 MySQL 的 `IN ... LIMIT` 限制） |

### 实测结果

| 指标 | 值 |
|---|---|
| 会话总数 | 826,508 → 压缩后 79 种路径 |
| 只浏览单步路径 | 546,512 会话（66.12%），转化率 0 |
| 直接购买路径（pv→buy） | 2.13% |
| 「其他路径组合」 | 21,043 会话，转化率 14.14%（长尾路径往往是完整决策旅程） |

| 类目转化差异 | Top10 类目浏览→购买 2.67%（2520377）~ 7.35%（4145813），相差近 3 倍 |

## 7. 性能基准评测：Pandas 内存计算 vs MySQL 库内聚合

```bash
python src/benchmark_compare.py       # 同一批分析任务两种技术路线各计时（约 7 分钟）
```

对 5 个典型分析任务（会话漏斗、用户画像聚合、逐日趋势、时段分布、类目聚合），
分别用 **Pandas 拉明细到内存计算**与 **MySQL 库内 SQL 聚合**两条路线计时
（各重复 2 次取最优），并核验两边结果总数完全一致。结果落盘
`output/benchmark_result.csv`。

### 实测结果（499 万行明细）

| 分析任务 | Pandas 内存计算 | MySQL 库内聚合 | 耗时比 |
|---|---|---|---|
| 会话级行为漏斗 | 0.586 s | 4.570 s | 0.13x |
| 用户画像特征聚合 | 3.610 s | 346.905 s | 0.01x |
| 逐日行为趋势 | 0.488 s | 23.546 s | 0.02x |
| 时段行为分布 | 0.459 s | 2.474 s | 0.19x |
| 类目行为聚合 | 0.285 s | 3.120 s | 0.09x |
| **合计**（另有一次性全量拉取 40.45 s） | **5.428 s** | **380.615 s** | — |

**结论**：本机 MySQL 无覆盖索引时，500 万行全表扫描聚合代价高昂；Pandas 一次性拉取
（40 s）后驻留内存，单任务仅 0.3~3.6 s，且同份数据反复复用不再付拉取成本。但明细
常驻内存不可持久——这正是本项目采用**『离线预计算聚合 → 小表落库 → 看板秒级读取』**
架构的实测依据：重计算交给离线步骤，在线只读预聚合小表，两种技术的优点各取所长。

## 9. 踩坑记录（都是实测踩出来的）

1. **文件按 `user_id` 排序，不是按时间排序**。不能"读到超出窗口就 break"，必须全量扫描；截取后必须显式排序，否则漏斗路径会错乱。
2. **数据集含脏时间戳**：最早 `1902-05-08`（甚至为负），最晚 `2037-04-09`，共 44,269 条。直接取 `min(timestamp)` 当窗口起点，窗口里只会捞到个位数数据。脚本用"峰值小时行数 × 0.5%"作阈值识别数据主区间来规避。
3. **`behavior_type` 的类别顺序必须固定**。若交给 pandas 自行推断，它会按**字母序**编码（buy=0, cart=1, fav=2, pv=3），而代码按 pv/fav/cart/buy 取 code，行为判断会整体错位且**不报错**。本项目统一传固定 `CategoricalDtype`。
   这个坑真实发生过：曾把"购买用户数 672,404"误当成"浏览用户数"，把基准漏斗算成 89% 而非 61%。
4. **覆盖索引是漏斗性能的关键**。只建 `idx_user_dt(user_id, dt)` 时，聚合要对每行回表随机读聚簇索引，实测 **62 秒**；加上 `idx_user_behavior_dt(user_id, behavior_type, dt)` 后降到 **0.85 秒**。会话汇总同理，加了 `idx_session_bhv_dt(session_id, behavior_type, dt)`。
5. **批量导入后必须 `ANALYZE TABLE`**，否则优化器统计过期，可能放弃覆盖索引改走回表计划，又退化回 62 秒。
6. **先导入后建索引**：`01_schema.sql` 只建主键，索引在 LOAD DATA 之后执行。
7. **`local_infile`**：服务端原值为 `0`，且 `secure_file_priv=D:\MySql\Uploads\` 限制在别处。脚本先记录原值、临时开启、导入后**还原为原值**，不留持久配置改动。
8. **换行符**：pandas 在 Windows 上写出的 CSV 是 CRLF，`LOAD DATA` 必须配 `LINES TERMINATED BY '\r\n'`（脚本自动探测）。
9. **中文路径**：工作区路径含中文，作为参数传给 `mysql.exe` 会在编码转换时损坏。脚本切到项目根目录、SQL 里只用 ASCII 相对路径，SQL 文本通过**标准输入**传给 `mysql.exe`。
10. **会话汇总的 `ord_mid` / `ord_buy` 不能用同一层 SELECT 里的别名**，须先聚合出 `has_*` 与 `t_*`，再在外层计算顺序标记。
11. **经典四层漏斗在会话级会"塌掉"**。若按「浏览→收藏→加购→购买」四步在同一次会话内严格依次要求，会话级总体转化率只有 0.08%——真实用户很少在一次会话里既收藏又加购再下单。这是口径选择问题而非数据问题，页面上同时给出会话级与用户级两个视角，并在文案里说明原因。
12. **商品分级的转化率极稀疏**。绝大多数商品转化率恰为 0，直接按转化率取"上下五分位"会把低档切出一大批零转化商品。`taobao_insights.py` 因此对参与分级的商品设了浏览量门槛（≥ 30），并要求低购买率商品流量不低于中位数，避免把"只被看过 2 次的商品"误判为低效商品。
13. **低购买率商品的流失定位要有参照物**。最初用「1 − 意向率」和「1 − 意向到购买率」直接比大小，结果 1,196 件商品全被归到同一类。改成与参评商品意向率的**中位数**比较后才有区分度（713 : 483），这才是可解释的归因规则。
14. **`GROUP_CONCAT` 不带分隔符会把序列压成一串字符**。提取会话行为序列时若不指定 `SEPARATOR ','`，pvfavcart 会拼成一个无界字符串，Python 端按字符压缩后路径代码变成 'p-v-p-v'。同时长路径会超出列宽报 `Data too long for column`，最终用「逗号分隔 + 长尾归并（< 200 会话的路径并入『其他路径组合』）」双管齐下解决。
15. **MySQL 8 的 `IN` 子查询不支持 `LIMIT`**（报 1235）。取 Top10 类目时须把 LIMIT 子查询外包一层派生表：`IN (SELECT category_id FROM (... LIMIT 10) top)`。另外 `CREATE TABLE AS SELECT` 不能与 `OR REPLACE` 连用，幂等建表只能先 DROP 再重建。
16. **性能预设要实测验证**。常规认知是"SQL 聚合优于内存计算"，但本机 MySQL 无覆盖索引时对 500 万行明细做 groupby 反而比 Pandas 内存计算慢 70 倍（380.6 s vs 5.4 s，结果完全一致）。评测脚本把两条路线的结果总数交叉核验，用数据确认了本项目「离线预计算 → 小表落库」架构的必要性，而不是想当然。
17. **离线画像标签直接进模型会造成标签泄漏**。购买预测初版 AUC 高达 1.0，排查发现特征里的 `rfm_score` 有 50% 权重来自购买频次分位（无购买用户恒为低分），等于把标签喂给了模型；剔除 buy_cnt 与 rfm_score 后 AUC 回落至 0.745 的真实水平。教训：复用上游画像字段前必须溯源其计算口径。
18. **"筛选方法好不好"不能由它自己的定义回答**。旧版高价值用户定义包含购买记录（has_buy=1 且 RFM 达标），用它验证"高价值组购买率更高"是同义反复。重建为不含购买信息的行为评分体系后，用与现有数据集零重叠的 25,407 名独立用户做前瞻性验证：得分十等位购买率从 47.51% 单调递增至 82.52%，方法才真正成立。
